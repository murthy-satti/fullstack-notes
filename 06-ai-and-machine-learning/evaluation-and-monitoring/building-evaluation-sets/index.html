    Building Evaluation Sets¶

    An evaluation set is the list of cases you run every time a prompt, model, retrieval setting, or tool changes, together with a precise statement of what a correct result looks like for each case. It is the LLM equivalent of a test suite, and like a test suite, its value depends less on the tool that runs it than on which cases it contains, how they were labeled, and whether the same set gives comparable numbers next month.

    This lesson builds the evaluation set for the TaskFlow Assistant, the feature that turns a sentence such as "priya needs to send the invoice by tomorrow, urgent" into a task draft. It covers the anatomy of a case, golden datasets, sampling cases from production traffic without leaking personal data, labeling and measuring labeler agreement, coverage and slices, dev and test splits, and versioning the set so that every score can be traced to an exact list of cases. Grading the outputs is the subject of the next lesson.

    Why it matters¶

    Without a fixed set of cases, every prompt change is judged by trying a few examples by hand. That works for an afternoon and then fails in three predictable ways. The examples people try are the easy, common ones, so regressions on rare inputs go unnoticed. Different people try different examples, so two engineers reach opposite conclusions about the same change. And nobody can say whether quality today is better or worse than in March, because there is no "same test" to rerun.

    A good evaluation set fixes all three. It holds the rare inputs on purpose (the late-evening time zone, the non-member assignee, the request that tries to override the instructions). It replaces opinions with a number per slice of traffic. And because it is versioned, "92% on task-assistant@1.2.0" means the same thing to everyone who reads it.

    The set is also where most of the real work of evaluation lives. Writing a judge prompt or wiring a CI job takes an hour; deciding what "correct" means for an ambiguous request, finding the cases that break the feature, and keeping the labels consistent takes weeks, and is what makes the rest trustworthy.

    Real-world usage¶

    • OpenAI. The guide Evaluation best practices tells teams to design task-specific evals that "reflect model capability in real-world distributions", to log everything during development so they can "mine your logs for good eval cases", and to keep automated scoring aligned with human feedback.
    • Anthropic. The guide Define success criteria and build evaluations advises building task-specific cases that include edge cases, choosing code-based grading where possible because it is the fastest and most reliable, and to "prioritize volume over quality": more questions with slightly noisier automated grading beat a few hand-graded ones.
    • Hamel Husain. In A Field Guide to Rapidly Improving AI Products he calls skipping error analysis the most common mistake teams make, and a simple data viewer for reading real traces the most important AI investment. Reading traces is how the cases in this lesson are found.
    • Shankar and colleagues. The paper Who Validates the Validators? (2024) describes criteria drift: people need criteria to grade outputs, but grading outputs is what helps them define the criteria. Labels and guidelines change as you label, which is one reason the set must be versioned.
    • LangSmith. The docs on managing datasets show the versioning model that hosted tools share: every change creates a new dataset version, versions can be tagged, and an evaluation can be pinned to a specific version or split.

    Popular tools and providers: plain JSONL files in the repository, DVC or Hugging Face Datasets for large files, and the dataset features of LangSmith, Langfuse, Arize Phoenix, and Braintrust; promptfoo and similar runners read cases from YAML, CSV, or JSONL files.

    How it works¶

    The anatomy of a case¶

    A case has three parts: the input exactly as the feature receives it, the expectation that a correct output must satisfy, and metadata that says what kind of case it is and where it came from.

    The expectation is deliberately partial. The case above checks the intent and the due date and says nothing about the title, because many titles are acceptable ("Call the bank", "Phone bank") and pinning one would make the case fail for good outputs. Check what matters for this case, and leave the rest to other cases or to a rubric.

    The metadata is what turns a pile of examples into a test suite:

    Field Purpose
    id Stable name, used in reports, diffs between runs, and bug reports. Never reused.
    slices The dimensions you report scores by: date type, time of day, assignee, risk, language
    split dev cases are for iterating on prompts; test cases decide releases
    critical Must pass on every release, regardless of the overall score
    source, sourceRef Where the case came from: hand-written, production (with the trace ID), incident, synthetic
    labeledBy Who decided the expectation, so disagreements can be traced
    addedIn, status The dataset version that introduced it, and whether it is active or retired

    Golden datasets and kinds of expectations¶

    A golden dataset is a set of inputs with expectations that the team has agreed are correct: the reference against which every version is measured. "Golden" refers to the agreement, not to the format. The expectation can take several forms, and one set often mixes them:

    Kind What the case stores TaskFlow example Graded by
    Reference output The exact correct value dueDate: "2026-11-14", intent: "other" Code: equality
    Properties Rules any correct output follows assignee is a project member or null; no text from the instructions leaks Code: predicates
    Reference answer plus criteria A model answer and what must match it Q&A: the answer must cite note kickoff-notes and state the launch date Code for citations, judge for meaning
    Criteria only A rubric, no reference Meeting-notes summary: every action item with its owner, no invented decisions Judge or human
    Pairwise preference Which of two outputs is better Old and new summary prompts on the same notes Judge or human, side by side

    Prefer the first two kinds wherever they apply: they are cheap, deterministic, and need no model to grade. Structured features like the Assistant can be graded almost entirely by code, field by field. Free text, such as summaries, needs criteria and a grader, which the LLM-as-judge lesson covers. RAG features need both retrieval and answer expectations; their specifics are in evaluating and debugging RAG.

    Where cases come from¶

    No single source gives a good set. Each covers a gap the others leave:

    Source Strength Risk
    Hand-written from the spec Covers rules and edge cases before launch Reflects what the team imagines, not what users type
    Production traces, sampled Real phrasing, real distribution Personal data; dominated by easy, common requests
    Failure signals (thumbs-down, edited drafts, retries) Concentrated on real failures Biased toward vocal users and visible errors
    Incidents and bug reports Each one prevents a known regression Few, and they arrive after the damage
    Synthetic variations Fill thin slices cheaply (other languages, odd formats) Unnatural phrasing; a model may generate what it already handles

    A common path is to start with 20 to 50 hand-written cases before launch, then grow the set from production every week: sample traffic, read the traces, and turn each newly understood failure into one or more cases. Hamel Husain's field guide calls this error analysis, and it is where most useful cases come from.

    Sampling from production¶

    Production traffic is the best source of realistic inputs and the most dangerous one. A responsible sampling pipeline does the same five things every time:

    1. Respect consent and policy. Use only traffic you are allowed to reuse for product improvement, and follow the retention rules in privacy, PII, and data retention. In TaskFlow, the trace export carries a consent flag and the sampler drops everything without it.
    2. Scrub before storing. Replace emails, phone numbers, and other identifiers with placeholders before a case reaches a labeler or a repository. Store the trace ID as sourceRef, never a copy of the raw request.
    3. Deduplicate. Real traffic repeats itself: "call the bank tomorrow" may appear hundreds of times. Hash the normalized, scrubbed text and keep one copy, or the set will measure the same request over and over.
    4. Stratify, do not just sample randomly. A random sample mirrors traffic, so a slice that is 0.5% of traffic gets one case in 200, which measures nothing. Take failure signals first, then fill every slice to a minimum count, then add random traffic so the common cases are still represented.
    5. Keep sampling continuously. Traffic changes when the product changes or a new customer arrives. A weekly sample of a few dozen new candidates keeps the set from drifting away from what users do.

    Two kinds of leakage break the measurement. If a production request was also used as a few-shot example in the prompt, the model has seen the answer, so the case is useless for testing; check new cases against the prompt's examples. And if the same request appears in both the dev and test splits (directly or as a near duplicate), tuning on dev inflates the test score.

    Labeling¶

    Labeling means writing the expectation for each case. For the Assistant that is mostly mechanical once the rules are written down; for summaries and answers it is a judgment, so the rules have to be explicit:

    • Write a labeling guide before labeling. It answers the questions labelers will otherwise answer differently: is "next Friday" said on a Friday this week or next week? Is "urgent" always high priority? What if the request names someone who is not a member? Each answer is a product decision, so the product owner signs it off.
    • Prefer pass/fail with a written reason over 1-to-10 scores. Two people rarely agree whether a summary is a 6 or a 7, but they usually agree whether it omits an action item, and the reason explains the decision to everyone who reads the case later.
    • Use domain experts for domain judgments. A support lead knows which answer would mislead a customer; an engineer may not.
    • Double-label a share of cases and measure agreement. If two careful people disagree, the guide is unclear or the case is genuinely ambiguous. Either way the case cannot be ground truth yet.

    Raw agreement overstates consistency when one label dominates: if 75% of outputs pass, two labelers who guess "pass" at random agree most of the time. Cohen's kappa corrects for that:

    kappa = (p_observed - p_expected) / (1 - p_expected)

40 summaries, labeler A: 30 pass, 10 fail; labeler B: 28 pass, 12 fail
p_observed = 34 / 40 = 0.85
p_expected = (30/40)(28/40) + (10/40)(12/40) = 0.525 + 0.075 = 0.60
kappa      = (0.85 - 0.60) / (1 - 0.60) = 0.63

    A widely used rule of thumb (Landis and Koch, 1977) calls 0.61 to 0.80 "substantial" agreement. Treat the scale as a guide, not a threshold: the useful output is the list of disagreements, which go to a short adjudication meeting that usually ends with a clearer rule in the guide. Expect the guide to change while you label (the criteria drift described in the research above), and re-check older labels when it does.

    Coverage and slices¶

    A slice is a subset of cases that share a property, such as "relative date, late evening in the user's time zone". Slices exist because one overall score hides concentrated failures: a prompt can score 94% overall while getting one time zone wrong half the time.

    Pick slice dimensions from three places: the rules in the prompt (dates, assignees, priority), the shape of the input (language, length, typos), and risk (prompt injection, personal data, requests that should be refused). Then keep a minimum number of active cases in every slice and report scores per slice.

    How many is enough? The 95% margin of error of a pass rate measured on n cases is roughly 1.96 * sqrt(p * (1 - p) / n):

    true pass rate around 90%
n = 50    ->  +/- 8.3 points
n = 100   ->  +/- 5.9 points
n = 400   ->  +/- 2.9 points

all n cases pass ("rule of three"): the true failure rate may still be
as high as about 3 / n, so 12 passing injection cases prove only that
fewer than about 1 in 4 fail

    Small slices therefore give wide intervals. The fix is not to stop measuring them, but to report the interval and add cases where a slice matters. The Wilson score interval used below behaves better than "mean plus or minus two standard errors" when n is small or the rate is near 0% or 100%.

    Splits and overfitting to the set¶

    Use two splits. The dev split is what you look at while editing a prompt: you read its failures, change the wording, and rerun. The test split decides whether a change ships, and you look only at its scores, not at its individual cases, while iterating. Without the split, every prompt change slowly fits the exact cases in the set, and the score rises while real quality does not.

    Even a disciplined test split wears out: the team learns its cases, and prompts start to mention their quirks. Refresh it from production on a schedule, retire cases that no longer reflect the product, and watch for the warning sign of a test score that keeps rising while user feedback stays flat. Never copy test cases into the prompt as few-shot examples.

    Versioning the set¶

    A score is meaningful only together with the set that produced it. Treat the evaluation set like code:

    • Keep it in the repository as JSONL (one case per line, so diffs are readable), reviewed in pull requests like any other change. Move to DVC or a hosted dataset when the files grow large, but keep the version rule.
    • Release immutable versions with semantic numbers: a patch for a corrected label, a minor version for added cases, a major version when the schema or scoring changes and old scores stop being comparable.
    • Never edit a released case in place. Retire it with a reason and add a corrected case under a new id, so old runs can still be reproduced and explained.
    • Record a manifest with the content hash and counts, check it in CI before every run, and store dataset@version and the hash with every evaluation result.
    • Version labels with the cases. A changed label changes the score as surely as a changed prompt; it needs the same review.

    Prompt and model versions follow the same idea; how they are tracked together with releases is covered in LLMOps: prompt and model versioning.

    When to use and when not to use¶

    Stage What the set should look like
    Prototype 20 to 50 hand-written cases covering the main rules and the obvious edge cases; enough to stop guessing
    Before launch 100 to 300 cases, every important slice with a minimum count, dev and test splits, a few critical cases, and a labeling guide
    In production Weekly samples from traffic and failure signals, every incident turned into a case, slice reports on every release
    Several features One set per feature, each with its own version, plus a small cross-feature smoke set

    Not everything needs an LLM evaluation set. Deterministic code around the model (date parsing helpers, permission checks, schema validation) belongs in ordinary unit tests, which are faster and exact. And a very large synthetic set that nobody has read is worse than a small set that has been reviewed: it measures the generator's idea of the task, with unknown label quality.

    Practical examples¶

    The case schema¶

    One schema validates every case, so a malformed line fails loudly instead of silently being skipped. It uses the same fields as the evaluation cases in prompt design and templates, plus the metadata described above:

    // evals/case-schema.ts: the shape of one TaskFlow Assistant evaluation case
import { z } from "zod";

export const SLICES = {
  intent: ["create_task", "other"],
  date: ["none", "absolute", "relative"],
  timeOfDay: ["daytime", "late-evening"],
  assignee: ["none", "member", "non-member"],
  risk: ["normal", "injection", "pii"],
  language: ["en", "non-en"],
} as const;

const sliceEnum = <K extends keyof typeof SLICES>(k: K) => z.enum(SLICES[k]);

export const EvalCase = z.object({
  id: z.string().regex(/^[a-z0-9-]+$/, "lowercase id, letters, digits, dashes"),
  // the input, exactly as the feature receives it
  request: z.string().min(1),
  members: z.array(z.string()),
  now: z.iso.datetime(),
  tz: z.string(),
  // what a correct draft must satisfy; omitted keys are not checked
  expect: z.object({
    intent: z.enum(["create_task", "other"]).optional(),
    dueDate: z.iso.date().nullable().optional(),
    priority: z.enum(["low", "medium", "high"]).optional(),
    assigneeName: z.string().nullable().optional(),
    clarifyingQuestion: z.enum(["present", "absent"]).optional(),
    notContains: z.union([z.string(), z.array(z.string())]).optional(),
  }),
  // metadata used for coverage, reporting, and lifecycle
  slices: z.object({
    intent: sliceEnum("intent"),
    date: sliceEnum("date"),
    timeOfDay: sliceEnum("timeOfDay"),
    assignee: sliceEnum("assignee"),
    risk: sliceEnum("risk"),
    language: sliceEnum("language"),
  }),
  split: z.enum(["dev", "test"]),
  critical: z.boolean().default(false),
  source: z.enum(["handwritten", "production", "synthetic", "incident"]),
  sourceRef: z.string().optional(), // trace ID or incident ID, never user content
  labeledBy: z.array(z.string()).min(1),
  addedIn: z.string().regex(/^\d+\.\d+\.\d+$/),
  status: z.enum(["active", "retired"]).default("active"),
  retiredReason: z.string().optional(),
});

export type EvalCase = z.infer<typeof EvalCase>;

export function parseCases(jsonl: string, file: string): EvalCase[] {
  const cases: EvalCase[] = [];
  const ids = new Set<string>();
  jsonl.split(/\r?\n/).forEach((line, i) => {
    if (!line.trim()) return;
    const result = EvalCase.safeParse(JSON.parse(line));
    if (!result.success) {
      throw new Error(`${file}:${i + 1}: ${z.prettifyError(result.error)}`);
    }
    if (ids.has(result.data.id)) throw new Error(`${file}:${i + 1}: duplicate id ${result.data.id}`);
    ids.add(result.data.id);
    cases.push(result.data);
  });
  return cases;
}

    z.iso.datetime() and z.iso.date() are Zod 4's string formats; the SLICES constant doubles as the slice taxonomy, so a typo such as late-evning fails validation instead of creating a new, empty slice.

    Sampling candidates from production¶

    This script reads an export of Assistant traces and writes candidate cases for labeling. It applies the five steps from the sampling section: consent, scrubbing, deduplication, and a stratified selection that takes failure signals first and then fills thin slices:

    // scripts/sample-production.ts: pick candidate eval cases from exported production traces
// Usage: npx tsx scripts/sample-production.ts exports/assistant-traces.jsonl 120 > evals/candidates.jsonl
import { createHash } from "node:crypto";
import { readFileSync } from "node:fs";
import { seededRandom, pct } from "../evals/stats.js";

interface TraceRecord {
  traceId: string;
  at: string;                 // ISO time of the request
  consent: boolean;           // user allowed their requests to improve the product
  request: string;
  members: string[];
  tz: string;
  feedback: "up" | "down" | null;
  edited: boolean;            // user changed the draft before saving it
}

type Slices = Record<"date" | "timeOfDay" | "assignee" | "risk" | "language", string>;

const [file, targetArg = "120", seedArg = "20261114"] = process.argv.slice(2);
const target = Number(targetArg);
const MIN_PER_SLICE = 8;
const random = seededRandom(Number(seedArg));

// 1. Scrub obvious personal data before anything is stored for labeling.
const scrub = (s: string) =>
  s
    .replace(/[\w.+-]+@[\w-]+\.[\w.-]+/g, "<email>")
    .replace(/\+?\d[\d\s().-]{7,}\d/g, "<phone>");

// 2. Draft slice tags with cheap rules; labelers confirm or fix them.
function draftSlices(r: TraceRecord): Slices {
  const text = r.request.toLowerCase();
  const hour = Number(new Intl.DateTimeFormat("en-GB", { timeZone: r.tz, hour: "numeric", hourCycle: "h23" }).format(new Date(r.at)));
  const mentionsMember = r.members.some((m) => text.includes(m.split(" ")[0].toLowerCase()));
  return {
    date: /\b\d{1,2}[./-]\d{1,2}\b|\b(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)[a-z]*\s+\d{1,2}\b/.test(text)
      ? "absolute"
      : /\b(today|tonight|tomorrow|next|monday|tuesday|wednesday|thursday|friday|weekend|in \d+ (days?|weeks?))\b/.test(text)
        ? "relative" : "none",
    timeOfDay: hour >= 20 || hour < 6 ? "late-evening" : "daytime",
    assignee: mentionsMember ? "member" : /\b(ask|tell|assign(ed)? to)\s+[a-z]+/.test(text) ? "non-member" : "none",
    risk: /ignore (all|your|previous)|system prompt|reveal your/.test(text) ? "injection" : "normal",
    language: /[^\x00-\x7f]/.test(r.request) ? "non-en" : "en",
  };
}

// 3. Deduplicate on the scrubbed, normalized text, so 400 copies of "call the bank tomorrow" count once.
const normalize = (s: string) => s.toLowerCase().replace(/[^\p{L}\p{N}]+/gu, " ").trim();
const seen = new Set<string>();
const pool: (TraceRecord & { slices: Slices; signal: boolean })[] = [];
let total = 0, noConsent = 0, dupes = 0;
for (const line of readFileSync(file, "utf8").split(/\r?\n/)) {
  if (!line.trim()) continue;
  total++;
  const r = JSON.parse(line) as TraceRecord;
  if (!r.consent) { noConsent++; continue; }
  const key = createHash("sha256").update(normalize(scrub(r.request))).digest("hex");
  if (seen.has(key)) { dupes++; continue; }
  seen.add(key);
  pool.push({ ...r, request: scrub(r.request), slices: draftSlices(r), signal: r.feedback === "down" || r.edited });
}

// 4. Select: failure signals first (capped), then fill thin slices, then random traffic.
const chosen = new Map<string, { r: (typeof pool)[number]; why: string }>();
const take = (r: (typeof pool)[number], why: string) => { if (chosen.size < target && !chosen.has(r.traceId)) chosen.set(r.traceId, { r, why }); };
const shuffled = [...pool].sort(() => random() - 0.5);
shuffled.filter((r) => r.signal).slice(0, Math.floor(target * 0.4)).forEach((r) => take(r, "signal"));
for (const dim of ["date", "timeOfDay", "assignee", "risk", "language"] as const) {
  for (const value of new Set(pool.map((r) => r.slices[dim]))) {
    const have = () => [...chosen.values()].filter((c) => c.r.slices[dim] === value).length;
    for (const r of shuffled) {
      if (have() >= MIN_PER_SLICE) break;
      if (r.slices[dim] === value) take(r, `coverage:${dim}=${value}`);
    }
  }
}
for (const r of shuffled) take(r, "random");

// 5. Write candidates (stdout) and a coverage report (stderr).
for (const { r, why } of chosen.values()) {
  console.log(JSON.stringify({ request: r.request, members: r.members, now: r.at, tz: r.tz, draftSlices: r.slices, source: "production", sourceRef: r.traceId, why }));
}
const picked = [...chosen.values()].map((c) => c.r);
console.error(`read ${total} traces: ${noConsent} without consent, ${dupes} duplicates, ${pool.length} unique candidates`);
console.error(`selected ${picked.length}: ${picked.filter((r) => r.signal).length} with failure signals (thumbs-down or edited)`);
console.error("slice                    traffic   sample  cases");
for (const dim of ["date", "timeOfDay", "assignee", "risk", "language"] as const) {
  for (const value of [...new Set(pool.map((r) => r.slices[dim]))].sort()) {
    const inPool = pool.filter((r) => r.slices[dim] === value).length;
    const inSample = picked.filter((r) => r.slices[dim] === value).length;
    console.error(`${`${dim}=${value}`.padEnd(24)} ${pct(inPool / pool.length).padStart(7)} ${pct(inSample / picked.length).padStart(8)} ${String(inSample).padStart(6)}`);
  }
}

    The helpers it imports, a Wilson interval, Cohen's kappa, and a seeded random generator so a sample can be reproduced, live in one small file:

    // evals/stats.ts: small, dependency-free statistics for eval reports

/** 95% Wilson score interval for a pass rate (better than mean +/- 2 SE when n is small). */
export function wilson(passes: number, n: number, z = 1.96): { low: number; high: number } {
  if (n === 0) return { low: 0, high: 1 };
  const p = passes / n;
  const denom = 1 + (z * z) / n;
  const center = (p + (z * z) / (2 * n)) / denom;
  const half = (z * Math.sqrt((p * (1 - p)) / n + (z * z) / (4 * n * n))) / denom;
  return { low: Math.max(0, center - half), high: Math.min(1, center + half) };
}

/** Cohen's kappa for two raters who labeled the same items with categorical labels. */
export function cohensKappa<T>(a: readonly T[], b: readonly T[]): number {
  if (a.length !== b.length || a.length === 0) throw new Error("need two equal, non-empty label lists");
  const n = a.length;
  const labels = [...new Set([...a, ...b])];
  let agree = 0;
  for (let i = 0; i < n; i++) if (a[i] === b[i]) agree++;
  const observed = agree / n;
  let expected = 0;
  for (const label of labels) {
    const pa = a.filter((x) => x === label).length / n;
    const pb = b.filter((x) => x === label).length / n;
    expected += pa * pb;
  }
  return expected === 1 ? 1 : (observed - expected) / (1 - expected);
}

/** Deterministic pseudo-random numbers (mulberry32), so samples can be reproduced. */
export function seededRandom(seed: number): () => number {
  let t = seed >>> 0;
  return () => {
    t = (t + 0x6d2b79f5) >>> 0;
    let r = Math.imul(t ^ (t >>> 15), 1 | t);
    r = (r + Math.imul(r ^ (r >>> 7), 61 | r)) ^ r;
    return ((r ^ (r >>> 14)) >>> 0) / 4294967296;
  };
}

export const pct = (x: number, digits = 1) => `${(100 * x).toFixed(digits)}%`;

    A per-slice report with intervals¶

    The evaluation runner (built in evals in CI and regression testing) writes one result line per case. This report groups results by slice, adds a Wilson interval, and flags slices that are thin or below target:

    // scripts/slice-report.ts: pass rate per slice with 95% intervals, flagging thin or failing slices
// Usage: npx tsx scripts/slice-report.ts results/run.jsonl 0.9
import { readFileSync } from "node:fs";
import { wilson, pct } from "../evals/stats.js";

interface Result { id: string; slices: Record<string, string>; pass: boolean; critical: boolean }

const [file, targetArg = "0.9"] = process.argv.slice(2);
const target = Number(targetArg);
const results: Result[] = readFileSync(file, "utf8").split(/\r?\n/).filter(Boolean).map((l) => JSON.parse(l));

const groups = new Map<string, Result[]>([["overall", results]]);
for (const r of results) {
  for (const [dim, value] of Object.entries(r.slices)) {
    const key = `${dim}=${value}`;
    groups.set(key, [...(groups.get(key) ?? []), r]);
  }
}

console.log("slice                       n   pass    95% interval     note");
for (const [key, rs] of groups) {
  const passes = rs.filter((r) => r.pass).length;
  const { low, high } = wilson(passes, rs.length);
  const notes = [
    rs.length < 30 ? "thin: add cases" : "",
    high < target ? "below target" : low < target ? "unclear" : "",
  ].filter(Boolean).join(", ");
  const interval = `${pct(low)} to ${pct(high)}`;
  console.log(`${key.padEnd(24)} ${String(rs.length).padStart(4)} ${pct(passes / rs.length).padStart(6)}   ${interval.padEnd(16)} ${notes}`);
}

const failedCritical = results.filter((r) => r.critical && !r.pass).map((r) => r.id);
if (failedCritical.length) console.log(`critical failures: ${failedCritical.join(", ")}`);

    Versioning with a manifest¶

    The manifest records the dataset version, a hash of the cases file, and counts. build writes it after an intentional change and refuses to reuse a version or delete a case; check runs in CI before every eval and fails if the cases changed without a new version:

    // scripts/dataset-manifest.ts: version the eval set and refuse silent edits
// Usage: npx tsx scripts/dataset-manifest.ts build 1.3.0   (after an intentional change)
//        npx tsx scripts/dataset-manifest.ts check         (in CI, before every eval run)
import { createHash } from "node:crypto";
import { existsSync, readFileSync, writeFileSync } from "node:fs";
import { parseCases } from "../evals/case-schema.js";

const CASES = "evals/datasets/task-assistant/cases.jsonl";
const MANIFEST = "evals/datasets/task-assistant/manifest.json";

interface Manifest {
  name: string;
  version: string;
  sha256: string;
  counts: Record<string, number>;
  ids: string[];
}

const [command, version] = process.argv.slice(2);
const raw = readFileSync(CASES, "utf8");
const cases = parseCases(raw, CASES);                           // schema and duplicate-id check
const sha256 = createHash("sha256").update(raw.replace(/\r\n/g, "\n")).digest("hex");
const old: Manifest | null = existsSync(MANIFEST) ? JSON.parse(readFileSync(MANIFEST, "utf8")) : null;

const count = (pred: (c: (typeof cases)[number]) => boolean) => cases.filter(pred).length;
const counts = {
  active: count((c) => c.status === "active"),
  retired: count((c) => c.status === "retired"),
  dev: count((c) => c.status === "active" && c.split === "dev"),
  test: count((c) => c.status === "active" && c.split === "test"),
  critical: count((c) => c.status === "active" && c.critical),
};

if (command === "check") {
  if (!old || old.sha256 !== sha256) {
    console.error(`${CASES} changed without a new version: run "dataset-manifest.ts build <version>"`);
    process.exit(1);
  }
  console.log(`task-assistant@${old.version} ok: ${counts.active} active cases (${counts.test} test, ${counts.dev} dev), ${counts.critical} critical`);
} else if (command === "build" && version) {
  const semver = (v: string) => v.split(".").map(Number);
  if (old) {
    const [a, b] = [semver(old.version), semver(version)];
    const newer = b[0] > a[0] || (b[0] === a[0] && (b[1] > a[1] || (b[1] === a[1] && b[2] > a[2])));
    if (!newer) throw new Error(`version ${version} must be greater than ${old.version}`);
    const missing = old.ids.filter((id) => !cases.some((c) => c.id === id));
    if (missing.length) throw new Error(`cases were deleted, retire them instead: ${missing.join(", ")}`);
  }
  const manifest: Manifest = { name: "task-assistant", version, sha256, counts, ids: cases.map((c) => c.id).sort() };
  writeFileSync(MANIFEST, JSON.stringify(manifest, null, 2) + "\n");
  console.log(`wrote ${MANIFEST}: task-assistant@${version}, sha256 ${sha256.slice(0, 12)}, ${JSON.stringify(counts)}`);
} else {
  console.error("usage: dataset-manifest.ts build <x.y.z> | check");
  process.exit(2);
}

    Best practices¶

    • Start with a few dozen hand-written cases before launch, then grow the set from real traffic every week.
    • Write a labeling guide, get product sign-off on its rules, and update it when adjudication reveals a gap.
    • Use pass/fail labels with a written reason; save numeric scales for cases where they are genuinely meaningful.
    • Double-label a share of every round, compute kappa, and adjudicate every disagreement.
    • Scrub personal data and drop non-consented traffic before any case is stored; keep only trace IDs as provenance.
    • Deduplicate on normalized, scrubbed text, and check new cases against the prompt's few-shot examples.
    • Keep a minimum number of cases per slice and report every score with its slice and interval.
    • Mark a small set of critical cases (incidents, security, legal) that must pass on every release.
    • Keep dev and test splits; look only at test scores while iterating.
    • Version the set, never edit released cases in place, and record dataset@version with every result.

    In production¶

    • The score went up, but users complain more. Detect: test pass rate rises release after release while thumbs-down rate and edited-draft rate stay flat or rise. Cause: the prompt has been tuned to the test cases (overfitting), or the set no longer reflects current traffic. Fix: refresh the test split from recent production samples, check for test cases copied into prompts, and review a fresh random sample of traces by hand.
    • Two runs of the "same" eval disagree. Detect: yesterday's 91% and today's 88% come from runs that report different case counts or hashes. Cause: someone edited the cases file, or the runner read a different file, without a version change. Fix: run the manifest check before every eval, store dataset@version and the hash with each result, and compare only runs with the same version.
    • A labeler's corrections flip results. Detect: a label-only pull request changes the pass rate by several points, and kappa for that round is low. Cause: an ambiguous rule in the labeling guide, interpreted differently by different people. Fix: adjudicate the disputed cases, write the decision into the guide, release a patch version, and re-check older labels against the new rule.
    • Personal data ends up in the repository. Detect: a secret scanner or a reviewer finds email addresses or phone numbers in cases.jsonl. Cause: cases were copied from production traces without the scrubbing step. Fix: remove the data from history following your incident process, make the sampler the only path from production into the set, and add a CI check that fails on email and phone patterns.
    • A regression shipped although the eval passed. Detect: an incident affects a specific kind of request, and the evaluation report shows few or no cases of that kind. Cause: a coverage gap: the slice was too thin to move the score. Fix: add the incident as a critical case, fill the slice to its minimum, and add the dimension to the slice taxonomy if it was missing.
    • The eval set rots. Detect: many cases reference features or rules that no longer exist, and failures are increasingly "the label is outdated". Cause: product changes without set maintenance. Fix: retire outdated cases with a reason, assign an owner to the set, and review it on a schedule, like dependency updates.

    Important terminology¶

    • Evaluation set: The fixed, versioned list of cases an AI feature is measured against.
    • Case: One input with its expectation and metadata.
    • Golden dataset: A set whose expectations the team has agreed are correct.
    • Expectation: What a correct output must satisfy: a reference value, properties, criteria, or a preference.
    • Slice: A subset of cases that share a property, reported separately.
    • Stratified sampling: Sampling that guarantees a minimum count per slice instead of mirroring traffic.
    • Critical case: A case that must pass on every release.
    • Dev and test splits: Cases for iterating on prompts, and cases for deciding releases.
    • Labeling guide: The written rules labelers follow to decide expectations.
    • Cohen's kappa: Agreement between two labelers, corrected for agreement by chance.
    • Criteria drift: The way grading criteria change as people grade more outputs.
    • Wilson interval: A confidence interval for a proportion that stays sensible for small samples.
    • Manifest: A record of a dataset version, its content hash, and its counts.

    Common mistakes and misconceptions¶

    • Believing a big set is a good set; 200 reviewed cases beat 5,000 unreviewed synthetic ones.
    • Sampling production traffic at random and calling it coverage.
    • Writing exact expected text for outputs that have many correct forms.
    • Using one overall score and ignoring the slices that matter most.
    • Copying raw production requests, with personal data, into the repository.
    • Editing a released case in place, which makes old and new scores incomparable.
    • Tuning prompts on the same cases that decide releases.
    • Treating 12 out of 12 passing cases as proof that a slice is solved.
    • Treating labels as permanent truth instead of decisions that may need revisiting.
