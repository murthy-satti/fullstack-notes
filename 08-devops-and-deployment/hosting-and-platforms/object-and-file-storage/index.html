    Object and File Storage¶

    Almost every application stores files: user uploads, exported reports, build artifacts, images, backups, logs. Where those bytes live decides how much you pay every month, how fast users can download them, and how hard it is to leave a provider later. This lesson explains the three kinds of cloud storage (object, block, and file), every major object store and its storage classes (Amazon S3, Cloudflare R2, Backblaze B2, Wasabi, Google Cloud Storage, Azure Blob Storage, DigitalOcean Spaces), the block and file services that sit next to virtual machines, the egress economics that decide most storage choices, and presigned uploads that keep large files off your API servers.

    It follows managed databases: databases hold structured records; this page covers everything that is a file. Archive tiers for backups get their own lesson in backup and archive storage.

    Why it matters¶

    Storage looks cheap on a pricing page, a few cents per gigabyte per month, so teams rarely think about it until the bill arrives. The bill is usually not driven by storage at all. It is driven by egress (data leaving the provider's network), by requests (millions of small reads and writes), and by retrieval and minimum-duration fees on the colder classes. A team that stores 10 TB of user files and lets users download 50 TB a month can pay more than $4,000 a month on one provider and under $200 on another, for the same bytes.

    The kind of storage also shapes the architecture. Object storage scales without limits and lets any number of servers share files, which is what makes stateless API servers possible. Block storage is a disk for one server. File storage is a shared network drive. Choosing the wrong one leads to classic failures: uploads saved on an instance's local disk that vanish when the instance is replaced, a shared filesystem used as a database, or a bucket of private documents left publicly readable.

    Real-world usage¶

    • Dropbox (Magic Pocket, 2016). In Scaling to exabytes and beyond Dropbox explains that it moved over 90% of its users' data from Amazon S3 to its own storage system, Magic Pocket. The reasons given are performance, the ability to customize the whole stack end to end for its workload, and better unit economics at its scale. It kept using AWS where that made sense, for example to store data in Germany for European business customers.
    • 37signals (2023-2025). In We stand to save $7m over five years from our cloud exit the company behind Basecamp reported a 2022 cloud bill of $3.2 million, just under $1 million of it for 8 PB in S3. In It's five grand a day to miss our S3 exit (March 2025) it reported spending just under $1.5 million a year on S3 and replacing it with about $1.5 million of storage hardware, and noted that AWS offered a free 60-day egress window for leaving. Storage at petabyte scale with steady growth is the case where owning hardware can win.
    • Cloudflare R2 (2021). Announcing Cloudflare R2 Storage states that R2 was built to cut the egress fees of typical cloud storage "to zero", describing those fees as charges "that don't correspond to any customer value". R2's pricing has no egress line at all, which is why it appears in the worked example below.
    • AWS (2024). Free data transfer out to internet when moving out of AWS announced that customers leaving AWS can request free data transfer out for that move. Egress fees are a real switching cost, and providers now treat them as part of the competitive and regulatory picture.

    Popular tools and providers: Amazon S3, Cloudflare R2, Backblaze B2, Wasabi, Google Cloud Storage, Azure Blob Storage, DigitalOcean Spaces, Ceph RADOS Gateway (self-hosted, S3-compatible), and the rclone and AWS CLI tools for moving data between them.

    How it works¶

    Object, block, and file storage¶

    Object storage Block storage File storage
    What you get Buckets of objects addressed by key over HTTPS A raw virtual disk attached to one server A shared network filesystem (NFS or SMB)
    How you use it PUT, GET, DELETE, LIST through an API or SDK Format it (ext4, XFS) and mount it like a local disk Mount it on many servers at once
    Who can read it Any client with permission, from anywhere The one server it is attached to (with rare exceptions) Every server that mounts it
    Edits Replace the whole object; no in-place edits Byte-level random reads and writes File-level reads and writes with locking
    Scale Practically unlimited; you never resize You choose a size and grow it Grows automatically on most managed services
    Typical latency Tens of milliseconds per request Sub-millisecond to a few milliseconds Low milliseconds
    Typical use Uploads, media, static assets, backups, data lakes Root disks, self-hosted databases Shared content for legacy apps, home directories, ML datasets
    Examples S3, R2, B2, Wasabi, GCS, Azure Blob, Spaces EBS, Persistent Disk and Hyperdisk, Azure Managed Disks EFS, FSx, Azure Files, Filestore

    The rule of thumb for a web application such as TaskFlow API: user files go to object storage, the database's disk is block storage (or a managed database that hides it), and file storage appears only when software insists on a shared POSIX filesystem.

    How object storage works underneath¶

    An object store is a giant key-value store for files. You create a bucket (a namespace with its own settings), then write objects under keys such as tasks/42/attachments/report.pdf. The slashes are part of the key; there are no real folders, only key prefixes that tools display as folders.

    • Immutable objects. You cannot change byte 500 of an object. You upload a new version of the whole object. Large files are uploaded in parts (multipart upload), so a failed part can be retried alone and parts can upload in parallel.
    • Durability by redundancy. Amazon S3 Standard is designed for 99.999999999% (eleven nines) durability and stores data across at least three Availability Zones. Providers use replication and erasure coding (splitting data into fragments plus parity, so lost fragments can be rebuilt) across many disks and buildings.
    • Consistency. Amazon S3 has provided strong read-after-write consistency since December 2020: after a successful write, every read returns the new object. Older articles that warn about eventual consistency in S3 are out of date.
    • Access control. Buckets are private by default. Access comes from identity policies, bucket policies, and short-lived presigned URLs that let a browser upload or download one object without credentials.
    • Metadata and features. Each object carries metadata (content type, custom headers). Buckets add versioning, lifecycle rules, replication, event notifications, and object lock (write-once retention).
    • S3 compatibility. The S3 API became the industry's common language. R2, B2, Wasabi, Spaces, GCS (through its XML API), and self-hosted Ceph accept S3-style requests, so the same SDK often works against all of them with a different endpoint. Compatibility is never total: check the provider's list of supported operations.

    Amazon S3 and its storage classes¶

    What it is. Amazon S3 (Simple Storage Service) is AWS's object store and the reference design for the whole category. You manage buckets, keys, permissions, lifecycle rules, and the choice of storage class per object; AWS manages the hardware, redundancy, scaling, and durability. A storage class is a per-object setting that trades storage price against access price and speed.

Requests on S3 Standard cost $0.005 per 1,000 writes and $0.0004 per 1,000 reads; the infrequent-access classes charge more per request ($0.01 per 1,000 writes on Standard-IA, $0.02 per 1,000 on Glacier Instant Retrieval). Durability, availability, and minimums are from the S3 user guide's storage class comparison.

    How the classes behave in practice:

    • Intelligent-Tiering watches each object. After 30 days without access it moves to the Infrequent Access tier, after 90 days to Archive Instant Access; optional Archive Access (90+ days) and Deep Archive Access (180+ days) tiers can be switched on for data that tolerates restores. Any read moves the object back to the frequent tier, with no retrieval fee. Objects under 128 KB are not monitored and always pay frequent-tier rates, so it suits large objects with unpredictable access. (How S3 Intelligent-Tiering works)
    • Minimums bite small objects. A 10 KB thumbnail in Standard-IA is billed as 128 KB, so it costs more than in Standard. Glacier Flexible Retrieval and Deep Archive add 40 KB of metadata per object (8 KB at the Standard rate), which dominates for millions of small files: bundle them into archives first.
    • One Zone classes keep a single copy set in one Availability Zone. The data is still durable against disk failures but is lost if that zone is destroyed. Use them only for data you can re-create, such as thumbnails or replicas.
    • Express One Zone is the high-performance class: single-digit millisecond access, lower request prices than Standard, but almost five times the storage price. It suits analytics and ML jobs that read the same data many times from compute in the same zone, not user uploads.

    Cloudflare R2¶

    What it is. R2 is Cloudflare's S3-compatible object store. It runs on Cloudflare's own network, which is also a large CDN, and its headline feature is no egress fees in any storage class. You manage buckets, keys, tokens, and lifecycle rules; Cloudflare manages everything else. Buckets can be exposed on a custom domain behind Cloudflare's cache, and Workers (edge functions) can read and write R2 directly.

    Pricing (R2 pricing): Standard storage $0.015 per GB-month, Class A operations (writes, lists) $4.50 per million, Class B operations (reads) $0.36 per million, egress free. Infrequent Access storage is $0.01 per GB-month with $9.00 and $0.90 per million operations, a $0.01 per GB retrieval fee, and a 30-day minimum. The monthly free tier covers 10 GB-month of Standard storage, 1 million Class A and 10 million Class B operations. Usage is rounded up to the next billing unit (1.1 GB-month is billed as 2).

    Trade-offs. No egress fees changes the economics for download-heavy apps. The downsides: fewer storage classes and no deep-archive tier, an S3 API that does not implement every operation (for example S3 Object Lock is listed as unimplemented; R2 has its own bucket locks), presigned URLs for GET, HEAD, PUT, and DELETE but not HTML form POST uploads, and a smaller compliance catalogue than the hyperscalers.

    Backblaze B2 Cloud Storage¶

    What it is. Backblaze B2 is an S3-compatible object store from a company that started in consumer backup. It has a single storage class and a deliberately simple price.

    Pricing (B2 pricing): $6.95 per TB per month, billed by byte-hour, with the first 10 GB free and no minimum file size or storage duration. Egress is free up to three times your average monthly stored data, then $0.01 per GB, and unlimited free egress applies when downloading through partner CDNs and compute providers (the page lists Fastly, Cloudflare, bunny.net, CacheFly, CoreWeave, Equinix Metal, Vultr, and phoenixNAP). Class A, B, and C API calls are free on pay-as-you-go; Class D calls cost $0.004 per 10,000 after 2,500 free per day.

    Trade-offs. Very cheap for storage-heavy data with moderate reads. Fewer regions than a hyperscaler, no storage classes or archive tier, and fewer surrounding services (no built-in event-driven compute next to the data).

    Wasabi Hot Cloud Storage¶

    What it is. Wasabi sells S3-compatible "hot" storage at a flat price per TB with no egress or API request fees.

    Pricing (Wasabi pricing): pay as you go from $7.99 per TB per month, with a minimum charge of 1 TB of active storage and a 90-day minimum storage duration (deleted data is billed as "timed deleted storage" until 90 days). Reserved capacity in 1-, 3-, or 5-year terms is cheaper and has a 30-day minimum.

    The egress catch. Egress is free under a policy: the pricing FAQ says that if your monthly egress is greater than your active storage, your use case "is not a good fit" for the free egress policy, and Wasabi reserves the right to limit or suspend service for regular overuse. Wasabi suits backups and archives that are written often and read rarely. It does not suit a public download site serving each file many times a month, unless a CDN in front absorbs most of the reads.

    DigitalOcean Spaces¶

    What it is. Spaces is DigitalOcean's S3-compatible object store with a built-in CDN, aimed at teams already running Droplets or App Platform.

    Pricing (Spaces pricing): a $5 monthly subscription includes 250 GiB of storage and 1,024 GiB of outbound transfer; extra storage is $0.02 per GiB-month and extra transfer $0.01 per GiB. The CDN is included, and its traffic counts against the same transfer allowance. Spaces Cold Storage costs $0.007 per GiB-month with a $0.01 per GiB retrieval fee (waived up to your average daily cold storage usage) and a 30-day minimum.

    Trade-offs. Predictable and simple, with a CDN in the box. Fewer regions and features than S3, and the $0.01 per GiB transfer price, while low, still adds up for heavy downloads.

    Google Cloud Storage¶

    What it is. Cloud Storage is Google Cloud's object store. Buckets are regional, dual-region, or multi-region, and each object has one of four classes. It integrates with BigQuery, Cloud Run, and Google's CDN products.

    Pricing (Cloud Storage pricing, us-central1 and us-east1): Standard $0.020 per GiB-month, Nearline $0.010 (30-day minimum, $0.01 per GiB retrieval), Coldline $0.004 (90 days, $0.02 per GiB), Archive $0.0012 (365 days, $0.05 per GiB). Operations on Standard cost $0.005 per 1,000 Class A and $0.0004 per 1,000 Class B. Unlike AWS's archive classes, every GCS class returns the first byte in milliseconds; the colder classes are cheaper to keep and dearer to read. Autoclass can move objects between classes automatically, and retrieval fees do not apply in Autoclass buckets.

    Azure Blob Storage¶

    What it is. Blob Storage is Azure's object store, organised as storage accounts that contain containers that contain blobs. Each block blob has an access tier.

    Pricing (Blob pricing, East US, locally redundant storage, from the Azure Retail Prices API): Hot $0.0208 per GB-month (first 50 TB), Cool $0.0152 (30-day minimum, $0.01 per GB read), Cold $0.0036 (90 days, $0.03 per GB), Archive $0.00099 (180 days, $0.02 per GB standard rehydration, $0.10 per GB high priority). Archive is offline: a blob must be rehydrated, which can take up to 15 hours (see Access tiers for blob data).

    Block storage: EBS, Persistent Disk, Managed Disks¶

    What it is. Block storage is a network-attached virtual disk. Amazon EBS, Google Cloud Persistent Disk and Hyperdisk, and Azure Managed Disks all work the same way: you create a volume of a chosen size and performance in one zone, attach it to a VM, and put a filesystem on it. The provider replicates the volume inside the zone; you manage the filesystem, resizing, and snapshots. A volume is tied to its zone, so a VM in another zone cannot attach it without restoring a snapshot.

    On AWS, the default gp3 volume costs $0.08 per GB-month and includes a baseline of 3,000 IOPS and 125 MB/s; extra IOPS cost $0.005 per provisioned IOPS-month and extra throughput $0.04 per provisioned MiB/s per month in us-east-1 (price list effective November 2026; see EBS pricing). Snapshots, which are incremental copies stored in S3, cost $0.05 per GB-month, or $0.0125 in the snapshot archive tier with a $0.03 per GB restore fee. Compare $0.08 for a block volume with $0.023 for S3 Standard: block storage is for data a running server needs as a disk, not for piles of files.

    File storage: EFS, FSx, Azure Files, Filestore¶

    What it is. Managed file storage is a network filesystem that many servers mount at once. Amazon EFS speaks NFS, grows and shrinks automatically, and spans zones; Amazon FSx offers managed Windows File Server, Lustre, NetApp ONTAP, and OpenZFS; Azure Files offers SMB and NFS shares; Google Cloud Filestore offers managed NFS. You manage mounts and permissions; the provider manages servers, replication, and capacity.

    EFS Standard storage costs $0.30 per GB-month in us-east-1, more than ten times S3 Standard, with infrequent-access and archive tiers and per-GB charges for elastic throughput (EFS pricing). Use shared file storage when software needs POSIX semantics: a CMS that writes uploads to a directory, a legacy app you cannot change, or a machine-learning job that reads a dataset as files. For new code, object storage is cheaper and scales further.

    Egress: the cost that decides most storage choices¶

    Storage is billed once per month per byte; egress is billed every time a byte is downloaded. For anything users download repeatedly (images, videos, exports, installers), egress quickly outgrows storage.

    Worked example. TaskFlow lets teams attach files to tasks. After two years it stores 10 TB (10,240 GB) of attachments, and users download 50 TB (51,200 GB) a month. Average file size is 5 MiB, so that is about 10.5 million downloads (10,485,760 GET requests). Monthly cost, US list prices:

    What the numbers teach:

    • Storage is the small part. Every option stores 10 TB for $70 to $236. The spread from $154 to $4,643 is almost entirely egress.
    • A CDN alone does not fix hyperscaler egress. CloudFront's pay-as-you-go rates are only a little below S3's direct rates. What changes the bill is a provider or plan whose model is not per-GB egress: R2, B2's partner egress, or CloudFront's flat-rate plans (launched November 2025; Free $0, Pro $15, Business $200, Premium $1,000 a month). Flat-rate plans cover one distribution, have no overage charges, and may reduce performance if you exceed the allowance, so read the terms and watch the usage alerts.
    • "Free egress" has conditions. B2's is free up to 3x storage or via partners; Wasabi's assumes egress stays at or below stored data; Spaces includes 1 TB. R2 has no egress line at all.
    • Requests matter for small files. At 5 MiB per file, requests cost a few dollars. Serve 100 KB thumbnails instead and the same 50 TB becomes about 537 million requests: R2 would bill about $190 in Class B operations and CloudFront about $527 in HTTPS requests.

    Presigned uploads: keep files off your servers¶

    If browsers upload files through the API, every byte crosses the API servers twice (in and out), ties up connections, and needs large request size limits. The standard pattern is a presigned upload:

    1. The browser asks TaskFlow API for permission to upload one file, sending its name, type, and size.
    2. The API checks the user's rights and the file type and size, chooses the object key itself (never trust a client-supplied path), and signs a short-lived upload URL or form with its own credentials.
    3. The browser uploads the bytes directly to the bucket.
    4. The browser (or a bucket event) tells the API the upload finished; the API records the key against the task, and optionally triggers a virus scan or thumbnail job.

    The bucket stays private: downloads use presigned GET URLs or a CDN with signed URLs. The application-side details (validation, scanning, private downloads) are in file storage and uploads and file uploads in Express; the code below shows the storage side.

    Millisecond reads by the same compute, many times S3 Express One Zone or block storage Cold classes with retrieval fees
    Data read rarely but instantly Standard-IA, Glacier Instant Retrieval, Nearline, Cool, R2 IA Archive tiers that need restores
    Heavy public downloads R2, B2 with a partner CDN, a flat-rate CDN plan Per-GB egress straight from a hyperscaler

    Which to choose¶

    Scenario Pick Runner-up Why
    Side project or portfolio Cloudflare R2 Backblaze B2 R2's free tier (10 GB, 10M reads) and zero egress cover most hobby sites at $0; B2 is just as cheap with 10 GB free
    Early startup on AWS S3 Standard plus lifecycle rules R2 for public downloads S3 integrates with IAM, Lambda, and the rest of the stack; move only download-heavy buckets if egress shows up on the bill
    Steady high traffic S3 or GCS behind a CDN with a committed or flat-rate CDN plan R2 At steady volume, negotiated or flat-rate delivery beats list egress; keep storage near compute
    Spiky traffic R2 or a flat-rate CDN plan S3 + CloudFront pay-as-you-go A viral file on per-GB egress becomes a surprise bill; zero or flat egress caps the risk
    Global audience Any object store behind a global CDN; R2 (Cloudflare network) S3 + CloudFront Users download from the nearest edge; the origin's region matters less than cache hit ratio
    Compliance-heavy (for example healthcare) S3, GCS, or Azure Blob under the provider's BAA The same in a dedicated, locked-down account AWS, Google Cloud, and Microsoft Azure state on their official pages that they sign a HIPAA BAA covering eligible services; for any smaller provider, use it for health data only if its official page offers a BAA for that product
    Large files and heavy egress R2 B2 with a partner CDN Egress is the bill (see the worked example)
    Team with no ops people The object store of the platform you already use (S3, Spaces, R2) Backblaze B2 One account, one bill, one set of credentials; nothing to operate either way

    Practical examples¶

    Presigned POST upload for TaskFlow attachments (S3)¶

    A presigned POST lets the bucket itself enforce limits: the signed policy fixes the key, the content type, and a size range, so a client cannot upload a 5 GB file with a URL meant for 25 MB.

    // src/storage/attachments.js: presigned uploads and downloads (Node 24, AWS SDK v3)
import { randomUUID } from "node:crypto";
import { S3Client, GetObjectCommand } from "@aws-sdk/client-s3";
import { createPresignedPost } from "@aws-sdk/s3-presigned-post";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: process.env.AWS_REGION });
const BUCKET = process.env.ATTACHMENTS_BUCKET;
const MAX_BYTES = 25 * 1024 * 1024; // 25 MiB
const ALLOWED_TYPES = new Set(["image/png", "image/jpeg", "application/pdf"]);

export async function createUploadForm({ taskId, contentType }) {
  if (!ALLOWED_TYPES.has(contentType)) {
    throw Object.assign(new Error("Unsupported file type"), { status: 400 });
  }
  // The server chooses the key; the client never controls the path.
  const key = `tasks/${taskId}/${randomUUID()}`;

  const { url, fields } = await createPresignedPost(s3, {
    Bucket: BUCKET,
    Key: key,
    Conditions: [
      ["content-length-range", 1, MAX_BYTES],
      ["eq", "$Content-Type", contentType],
    ],
    Fields: { "Content-Type": contentType },
    Expires: 300, // seconds
  });
  return { url, fields, key };
}

export function createDownloadUrl(key, filename) {
  const command = new GetObjectCommand({
    Bucket: BUCKET,
    Key: key,
    ResponseContentDisposition: `attachment; filename="${filename.replace(/"/g, "")}"`,
  });
  return getSignedUrl(s3, command, { expiresIn: 300 });
}
    • content-length-range makes S3 reject bodies outside 1 byte to 25 MiB.
    • eq $Content-Type stops a client from uploading HTML or SVG under an image key, which would otherwise be a stored cross-site scripting risk if the file were ever served inline.
    • Expires: 300 keeps a leaked form useless after five minutes.
    • ResponseContentDisposition forces downloads instead of rendering the file in the browser.

    The browser sends every returned field, then the file last (S3 ignores form fields after the file):

    // web/src/upload.js: TaskFlow Web uploads directly to the bucket
export async function uploadAttachment(taskId, file) {
  const res = await fetch(`/api/tasks/${taskId}/attachments/upload-form`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ contentType: file.type }),
  });
  if (!res.ok) throw new Error("Could not start upload");
  const { url, fields, key } = await res.json();

  const form = new FormData();
  for (const [name, value] of Object.entries(fields)) form.append(name, value);
  form.append("file", file); // must be the last field

  const upload = await fetch(url, { method: "POST", body: form });
  if (!upload.ok) throw new Error(`Upload rejected: ${upload.status}`);
  return key; // then tell the API the upload finished
}

    Bucket CORS for browser uploads¶

    Browsers block cross-origin requests unless the bucket allows the app's origin:

    {
  "CORSRules": [
    {
      "AllowedOrigins": ["https://app.example.com"],
      "AllowedMethods": ["GET", "PUT", "POST"],
      "AllowedHeaders": ["*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3000
    }
  ]
}

    # Apply the CORS rules to the attachments bucket
aws s3api put-bucket-cors \
  --bucket taskflow-attachments \
  --cors-configuration file://cors.json

    List exact origins. * would let any website use your upload endpoint with a leaked form.

    The same code against Cloudflare R2¶

    R2 speaks the S3 API, so only the client changes. R2 presigned URLs support GET, HEAD, PUT, and DELETE, with an expiry from 1 second to 7 days; HTML form POST uploads are not supported, so use a presigned PUT:

    // src/storage/r2.js: presigned PUT against Cloudflare R2
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const r2 = new S3Client({
  region: "auto", // required by the SDK, ignored by R2
  endpoint: `https://${process.env.R2_ACCOUNT_ID}.r2.cloudflarestorage.com`,
  credentials: {
    accessKeyId: process.env.R2_ACCESS_KEY_ID,
    secretAccessKey: process.env.R2_SECRET_ACCESS_KEY,
  },
});

export function createR2UploadUrl(key, contentType) {
  // The client must send the same Content-Type header, or R2 rejects the upload.
  const command = new PutObjectCommand({
    Bucket: process.env.R2_BUCKET,
    Key: key,
    ContentType: contentType,
  });
  return getSignedUrl(r2, command, { expiresIn: 300 });
}

    A presigned PUT cannot enforce a size range the way a POST policy can. Check the object's size after upload (a HEAD request or an event notification) and delete anything over the limit.

    # .env for local development against R2 (placeholders only)
R2_ACCOUNT_ID=<account-id>
R2_ACCESS_KEY_ID=<access-key-id>
R2_SECRET_ACCESS_KEY=<secret-access-key>
R2_BUCKET=taskflow-attachments

    Lifecycle rules for an uploads bucket¶

    Attachments are read often for a few weeks, then rarely. This rule moves them to Intelligent-Tiering after a week (most are over 128 KB), deletes old versions, and cleans up abandoned multipart uploads, which are billed as storage but invisible in normal listings:

    {
  "Rules": [
    {
      "ID": "attachments-tiering",
      "Filter": { "Prefix": "tasks/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 7, "StorageClass": "INTELLIGENT_TIERING" }
      ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

    aws s3api put-bucket-lifecycle-configuration \
  --bucket taskflow-attachments \
  --lifecycle-configuration file://lifecycle.json

    Archive-tier rules (Glacier, Deep Archive) and retention locks are covered in backup and archive storage.

    Mounting shared file storage (EFS)¶

    When an off-the-shelf app needs a shared directory, mount EFS on every instance with the Amazon EFS mount helper and TLS:

    # On each instance (Amazon Linux): install the helper, mount, and persist
sudo dnf install -y amazon-efs-utils
sudo mkdir -p /mnt/shared
sudo mount -t efs -o tls fs-<id>:/ /mnt/shared
echo "fs-<id>:/ /mnt/shared efs _netdev,noresvport,tls 0 0" | sudo tee -a /etc/fstab

    Best practices¶

    • Keep buckets private, turn on S3 Block Public Access (or the provider's equivalent) at the account level, and serve public files through a CDN.
    • Let the server choose object keys; include tenant and task IDs in the key so permissions and lifecycle rules can target prefixes.
    • Use presigned uploads with short expiry and enforced size and type; never proxy large uploads through the API.
    • Estimate egress before choosing a provider: multiply expected downloads by file size, then price it on two or three providers.
    • Put a CDN in front of anything public and measure the cache hit ratio; every miss is origin egress and a request.
    • Add lifecycle rules on day one: abort incomplete multipart uploads, expire old versions, and tier data by age.
    • Respect minimums: do not put small or short-lived objects in IA or archive classes.
    • Tag buckets by owner and environment so storage shows up per team on the bill (see cost optimization).
    • Use the S3 API through an SDK with a configurable endpoint, so moving between S3-compatible providers is a configuration change.

    In production¶

    • The storage bill is ten times what storage should cost. Detect: Cost Explorer grouped by usage type shows DataTransfer-Out-Bytes or CloudFront data transfer as the top line, not TimedStorage-ByteHrs. Cause: download-heavy files served on per-GB egress, often through a public bucket that bypasses the CDN. Fix: serve through a CDN with a high hit ratio, move public downloads to a zero-egress store or flat-rate plan, and block direct bucket access.
    • Storage keeps growing although users delete files. Detect: S3 Storage Lens or bucket metrics show noncurrent version bytes or incomplete multipart upload bytes rising. Cause: versioning keeps every overwritten and deleted object; failed uploads leave parts behind. Fix: add NoncurrentVersionExpiration and AbortIncompleteMultipartUpload lifecycle rules.
    • Moving to Standard-IA made the bill go up. Detect: new EarlyDelete-SIA, TimedStorage-SIA-SmObjects, and Retrieval-SIA usage types appear after the change. Cause: many objects were under 128 KB, were deleted within 30 days, or were read often. Fix: use Intelligent-Tiering for unknown access, or filter transitions by object size and age; analyse access with S3 Storage Class Analysis first.
    • Browser uploads fail with a CORS error after a domain change. Detect: the browser console shows a blocked preflight to the bucket endpoint; the bucket's CORS rules list the old origin. Cause: bucket CORS is separate from the API's CORS. Fix: add the new origin to the bucket's CORS configuration and redeploy.
    • Uploaded files disappear after a deploy. Detect: files referenced in the database return 404; the instances or containers were replaced. Cause: uploads were written to the local disk of an instance or container. Fix: write uploads to object storage; treat servers as disposable.
    • A bucket of private documents is found publicly readable. Detect: an external report, AWS Trusted Advisor or IAM Access Analyzer findings, or aws s3api get-bucket-policy-status returning IsPublic: true. Cause: a bucket policy or ACL granting * read, often added to "make images work". Fix: enable Block Public Access, remove the grant, serve through a CDN with origin access control, rotate any exposed data, and treat it as a security incident.

    Important terminology¶

    • Object storage: Storage of whole files (objects) under keys in buckets, accessed over an HTTP API.
    • Block storage: A network-attached virtual disk for one server.
    • File storage: A shared network filesystem mounted by many servers.
    • Bucket: A named container for objects with its own settings.
    • Key: The full name of an object, including any / prefixes.
    • Storage class / access tier: A per-object setting trading storage price against access price and speed.
    • Egress: Data transferred out of a provider's network, usually billed per GB.
    • Minimum storage duration: The period an object is billed for even if deleted sooner.
    • Minimum billable object size: The size small objects are billed at in some classes (128 KB on S3 IA classes).
    • Presigned URL: A time-limited URL signed with server credentials that allows one specific request without credentials.
    • Multipart upload: Uploading a large object in independently retryable parts.
    • S3-compatible: A non-AWS service that accepts S3 API requests.

    Common mistakes and misconceptions¶

    • Comparing providers on storage price alone, when egress and requests dominate download-heavy workloads.
    • Believing a CDN automatically removes egress costs; on per-GB CDN pricing it mostly moves them.
    • Assuming "free egress" is unconditional; read the multiplier, the partner list, or the fair-use policy.
    • Putting small or short-lived objects into IA or archive classes and paying minimums.
    • Storing uploads on instance disks or in container filesystems.
    • Using EFS as a cheap object store; it costs more than ten times as much per GB as S3 Standard.
    • Making a bucket public to serve images instead of using a CDN with origin access control.
    • Assuming every "S3-compatible" service supports every S3 feature (POST policies, Object Lock, event notifications).
