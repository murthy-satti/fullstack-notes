    Hosting and Cloud Platforms¶

    Hosting is the decision about where your software runs and where its data lives: on a virtual machine you manage, in containers on a managed service, as functions that run per request, as static files on a CDN, or on a developer platform that hides all of that behind git push. Every option trades control for convenience and a predictable bill for one that follows your traffic. This subject explains what each option is, what you manage and what the provider manages, how each one bills, which well-known companies use it and why, and how to pick one for a given situation.

    What hosting and cloud platforms provide¶

    • Compute: virtual machines, containers, functions, and edge runtimes that run your code, from one small server to thousands of instances.
    • Managed data services: relational and document databases, caches, queues, and object storage that someone else patches, backs up, and fails over.
    • Delivery: load balancers, CDNs, TLS certificates, and DNS that put your application in front of users worldwide.
    • Elasticity: capacity you can add in minutes and remove when traffic drops, so you pay for what you use instead of buying for the peak.
    • Compliance building blocks: audited data centers, encryption, and contracts (such as a HIPAA Business Associate Agreement) that you could not easily build yourself.

    Each of these also creates a bill with several meters (instance-hours, requests, GB-seconds, GB stored, GB transferred), responsibilities you keep (your code, your data, your access settings), and some degree of lock-in to the provider's APIs.

    How a typical hosting decision works¶

    1. List the workloads. For TaskFlow these are a React frontend (TaskFlow Web), a Node.js API (TaskFlow API), a MongoDB database, uploaded files, and a few background jobs.
    2. Pick a level of control for each. Static files rarely need a server; an API can run on a platform, in containers, or as functions; a database is almost always better managed.
    3. Check the hard constraints: long-lived WebSocket connections, request duration limits, data residency, compliance contracts, and the regions your users are in.
    4. Price it with real units for your expected traffic, including the meters people forget: data transfer out, NAT gateways, load balancer hours, public IPv4 addresses, and log ingestion.
    5. Estimate the exit cost: how much code and data would have to change to move, and what moving the data out would cost in egress fees.
    6. Start with the simplest option that meets the constraints, write down the traffic or cost level at which you would revisit it, and measure.

    Practical example¶

    The same TaskFlow API container image can run on several of these options. On Google Cloud Run, one command deploys it as a serverless container that scales to zero when idle:

    # Deploy the TaskFlow API image to Cloud Run (request-based billing)
gcloud run deploy taskflow-api \
  --image=us-docker.pkg.dev/example-project/apps/taskflow-api:1.4.0 \
  --region=us-central1 \
  --port=3000 \
  --cpu=1 --memory=512Mi \
  --min-instances=0 --max-instances=10 \
  --set-secrets=MONGODB_URI=taskflow-mongodb-uri:latest \
  --allow-unauthenticated

  memory          200,000 GiB-s, under the 360,000 GiB-s free tier      = $0.00

    Requests that overlap on one instance share billable time, so the real figure is usually lower. The same image could run on AWS Fargate behind a load balancer for a steady monthly price, or on a $12 virtual machine. Which one is cheapest depends on traffic shape, and the backend servers lesson works out where the lines cross.

    Developer perspective and common misconceptions¶

    Choose per workload, not per company: static files on a CDN, the API on whatever your team can operate well, and the database on a managed service. Keep the application portable where it is cheap to do so (a container image, standard SQL or the MongoDB wire protocol, environment configuration), and accept lock-in deliberately where it buys real value. Put a budget alert on every account on day one.

    • "Serverless is always cheaper." It is cheapest at low or spiky traffic; at steady high traffic, per-request pricing usually costs more than instances that run all month.
    • "The cloud is always more expensive than your own servers." For small teams, the operations work you avoid usually outweighs the price difference; the comparison changes only at large, steady scale.
    • "The price on the pricing page is the bill." Data transfer, NAT gateways, load balancers, logs, and idle resources often add more than the compute itself.
    • "A managed service means no operations." You still own schema design, capacity choices, access control, cost, and restore testing.
    • "Free tiers are a hosting plan." Many free tiers sleep, expire, or forbid commercial use; read the limits before launching on one.
